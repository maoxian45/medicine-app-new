沿用模板，每个功能用例一张表：

| 模板项目 | 填写内容 |
| --- | --- |
| 用例唯一标识 | 统一编号 |
| 用例描述（功能描述） | 本用例验证的功能 |
| 环境描述 | 浏览器、系统、前后端服务状态 |
| 实例编号 | 本用例的场景/数据编号 |
| 操作步骤 | 可复现的输入和点击步骤 |
| 期望输出 | 操作前定义的预期结果 |

| 测试人员、测试时间 | 实际执行人员和日期 |
| 备注 | 关联需求/模块、前置数据、失败原因、修复和复测情况 |

最终由 sjw 统一编号、目录和格式后合并；wzy 对自己的表格内容和数据核验负责。未实现或未执行项如实标记，不能预填“与期望相符”。

## 文档交付

1. 四人各写自己包的个人详细设计，类/函数/字段必须与最终代码一致。一个人多个包的合并或分册方式，以老师最终要求为准。
2. 系统测试文档沿用现有 Word 模板，以测试用例表编排；sjw 和 wzy 各自负责明确的一部分，完成后合并成一份。qhy、wmx 提供必要说明并修复自己代码的问题，不承担公共测试表的撰写。若老师另要求个人测试文档，再按要求整理。
3. 每条系统测试填写：用例编号、关联需求/模块、环境、前置数据、步骤、预期、实际、截图、测试人、时间、问题和复测结果。
4. 自动化测试作为辅助证据，不代替浏览器操作记录。未实现项不得填写通过。
5. 每个人验证自己的代码并修复自己文件的问题；开发量较大的 UI/服务负责人少承担公共测试文档整理。
6. 药品来源资料由四人共同整理，统一模板；wzy 导入，知识管理员核对并发布，不把演示资料当作专业医学审定。

## 推进顺序

1. 固定验收范围：对照 `docs/文档功能对照.md`；保留为必做的需求必须实现，延期项同步修改需求及测试范围。
2. 先通用户流程：成员 → 图片识别 → 核对成分 → 风险检查 → 确认入箱 → 知识/AI → 提醒 → 确认 → 历史 → 撤销。
3. 再通管理流程：新增草稿 → 审核发布 → 用户查询/风险生效 → 修改/停用 → 检查历史版本。
4. 功能稳定后集中执行系统测试，修复后复测，最后对齐个人详细设计和实际代码。
