# frontend-药明白前端简要说明

## 1. 当前前端已经完成的主要流程

前端目前的核心流程是：

```text
拍照 / 相册选图 / 搜索药品
→ 前端用 iOS Vision 做 OCR
→ 前端把 OCR 原文发给后端解析接口
→ 后端返回结构化用药信息
→ 前端展示待核对用药卡片
→ 用户确认
→ 加入家庭药箱
→ 设置提醒
→ 确认服药 / 取消误点
```

前端不会自动把识别结果加入药箱，必须用户核对后保存。

前端不展示“常见药品样例 / 常见药品推荐”。这类模块容易被误解为用药推荐，不适合医疗健康类 App。加药页只保留拍照识别、相册识别、药名查询、手动核对和安全边界说明。

---

## 2. 前端页面逻辑

### 首页

首页只放用户常用入口：

- 识别 / 查询
- 设置提醒
- 提醒列表
- 家庭药箱
- 今日用药状态

首页的“待服药”表示：今天有提醒，但用户还没有点击“确认”。这个确认只代表“确认已服药 / 记录服药完成”，入口在首页展开后的今日用药明细、提醒列表和老人模式的“我已经吃药了”。

首页的“需处理”表示家庭药箱里有药品需要关注，可能是药品信息待核对、即将过期、库存不足或风险标签。它不是服药确认入口。药品信息待核对时，用户可以从首页风险卡或家庭药箱进入药品详情，在“基础信息”里点击“编辑药箱信息”修改库存、位置、使用者、有效期等；确认无误后可把“当前状态”改为“正常”，或直接点击“信息已核对，标记正常”。

首页不显示后端连接状态，也不显示开发调试信息。

### 识别 / 查询

用户可以拍照、选图或搜索药品。

OCR 当前在 iOS 端使用 Vision 完成，前端只把识别出来的文字发给后端解析，不上传图片文件。

前端会把 OCR 结果发给后端：

```text
POST /api/instruction/parse
```

请求：

```json
{
  "ocr_text": "Vision识别出的说明书文字"
}
```

后端返回药品信息后，前端展示用药卡片。

如果图片没有识别出文字，前端会停留在识别页提示重新拍摄，不会自动使用某个示例药品兜底，避免 OCR 测试时出现“看似识别成功但实际是演示数据”的情况。

前端会在用药卡片中保留并展示 `original_text` / OCR 原文，方便判断问题来源：

- 如果 OCR 原文本身错字多、漏字多、顺序乱，主要是前端 Vision OCR 或图片质量问题。
- 如果 OCR 原文基本正确，但药名、剂量、频次、禁忌、注意事项等字段解析错误，主要是后端 `/api/instruction/parse` 的结构化解析问题。

目前测试反馈倾向于：OCR 原文可以拿到，但结构化结果质量差，因此当前优先认为是后端解析问题。

真机使用相机需要 Info.plist 权限说明，当前 Xcode 工程已通过 generated Info.plist build setting 配置：

```text
NSCameraUsageDescription
NSPhotoLibraryUsageDescription
```

### 用药卡片

展示：

- 药名
- 规格
- 用量
- 频次
- 饭前 / 饭后
- 服用方式
- 贮藏方式
- 有效期
- 风险提示
- 禁忌
- 注意事项
- OCR 识别原文
- 语音播报内容

用户核对后，才能加入家庭药箱。

如果后端无法可靠解析，不要返回布洛芬等演示药品兜底数据。可以返回“待确认药品”或空字段，并通过 `needs_confirmation = true`、`fallback_fields` 告诉前端哪些字段需要人工核对。

### 家庭药箱

家庭药箱支持：

- 添加药品
- 查看药品
- 编辑已保存药品的使用者、位置、库存、有效期、用量、频次、状态和备注
- 将“需确认 / 识别不完整”的药品标记为“正常”
- 删除药品 / 删除已合并药品组
- 相同药品合并显示
- 显示库存
- 显示存放位置
- 显示有效期状态

添加药品时，用户必须选择：

- 给谁用
- 家中放在哪里

“给谁用”支持选择“全部人”。“全部人”表示家庭共享药品，可以出现在家庭药箱和各成员可用药列表中。

但设置服药提醒时，必须选择具体成员，不能选择“全部人”。服药确认必须落到某一个真实成员身上。

列表和详情页的库存展示都按相同合并规则计算；例如同一药品同成员、同规格、同位置下有两条 16 粒记录时，列表和详情都会显示 32 粒。

修改已保存药品时，入口在家庭药箱列表 → 药品详情 → “编辑药箱信息”。编辑保存走 `PUT /api/medicines/{medicine_id}`，不会走新增接口；这可以避免“修改库存/位置/使用者”时误创建重复药品。

如果某张详情页来自合并后的药品卡，删除按钮会按“删除这组药品”处理，避免列表显示一张合并卡、详情只删除其中一条导致返回后仍剩半组库存。编辑按钮默认编辑当前详情页代表的那条药品记录；如果后续产品希望“一次编辑整组合并药品”，需要后端提供批量更新能力。

### 家庭成员

家庭成员页支持：

- 查看成员用药状态
- 新增家庭成员
- 左划删除家庭成员
- 在提醒、药箱保存时使用成员名单

前端不再做“成人用药 / 儿童用药”的介绍型页面或分类文案，成员身份只作为家庭管理备注使用。

成员列表采用类似微信的左划删除：左划成员卡片后，在右侧露出红色“删除”按钮，再二次确认。不是整张卡片直接变成删除态。

删除成员目前只从前端列表移除，不会删除该成员已有药品、提醒和服药记录。若后端补齐删除接口，前端会自动调用。

### 儿童喂药记录

家庭成员被识别为儿童时（角色含“儿童 / 孩子 / 宝宝”、使用婴儿头像，或年龄小于 18 岁），点击该成员会进入儿童喂药记录页，不再跳到普通提醒列表。

当前前端已接入：

- 展示该儿童的真实年龄和体重。
- 从家庭药箱选择属于该儿童或“全部人”的药品。
- 按儿童和药品筛选今日真实服药记录。
- 二次确认后通过现有 `POST /api/records` 保存喂药记录。
- 将选中的儿童和药品带入现有提醒设置页，自由选择下次提醒时间。
- 明确提示该功能只记录和防重复，不自动判断儿童剂量或再次用药时机。

当前后端 `GET /api/records` 默认只返回当天记录，因此页面暂时展示“今日时间轴”。要实现作品说明中的跨日/本周记录和多照护者同步详情，后端仍需支持按成员、药品和日期范围查询，并给记录增加 `medicine_id`、`member_id`、`recorded_by`、`temperature` 和 `note`。
### 设置提醒

新增提醒时，用户必须选择：

- 服药对象
- 具体药品
- 每日提醒次数
- 每次提醒的具体时间（小时和分钟可自由选择）
- 用量

不能默认选择布洛芬。

如果从“爷爷”页面进入设置提醒，会自动选中“爷爷”，但药品仍然要用户自己选。

如果从某个药品详情进入设置提醒，可以自动选中这个药品。

共享药品，即 `owner = "全部人"` 的药，可以被具体成员拿来设置提醒；但提醒本身必须绑定具体成员，例如“爷爷 08:00 吃 1 片”。

提醒时间已经改为系统时间选择器。用户先选择每日 1 / 2 / 3 次，再分别自由选择每次提醒的小时和分钟；提交给后端的 `time` 仍为 `HH:mm`，现有提醒接口无需因 TimePicker 改动。

### 药品日期与到期日计算

加入或编辑药品时支持两种方式：

- 包装直接标注明确到期日：用户直接选择 `expiry_date`。
- OCR 识别到“36个月 / 2年 / 90天”等保质期：生产日期为可选项；未填写时直接展示保质期，填写后由前端计算最终到期日。

前端把三个含义分开：

- `production_date`：可选生产日期，填写时使用 `yyyy-MM-dd`。
- `shelf_life`：包装或说明书标注的保质期原值，例如 `36个月`。
- `expiry_date`：前端计算或用户直接选择的最终到期日期，`yyyy-MM-dd`；只有保质期但没有生产日期时为空。

`BackendClient` 已发送并兼容读取以上字段。为了兼容尚未增加 `shelf_life` 的旧后端，没有具体日期时会暂时通过 `expiry_date` 保存“36个月”等保质期；读取时前端会重新识别为 `shelfLife`，因此刷新后仍可展示。后端完成结构化字段升级后，应把这类历史值迁移到 `shelf_life`。

展示优先级为：有具体 `expiry_date` 时显示具体日期；否则显示 `shelf_life`。只有具体日期才能参与临期判断。

### 提醒列表

提醒列表支持：

- 查看提醒
- 标记已服药
- 取消已服药
- 删除提醒

用户误点“已服药”后，可以取消。

### 老人模式

老人模式是独立模式，不是普通页面里的一个小入口。

老人模式只保留简单操作：

- 今天吃药
- 我的药
- 找家人
- 听一遍
- 我已经吃药了
- 点错了，取消

不显示“大字、少按钮”等介绍性文案。

老人模式必须绑定当前老人身份。当前是“爷爷”时，只能看到并操作“爷爷”的提醒；不能确认“我”、奶奶或其他成员的用药。

前端已经做了页面过滤和操作函数二次校验，但后端也应该做同样的成员归属校验，避免只靠前端限制。

## 3. 后端需要做什么

### P0：优先修复说明书解析接口

接口：

```text
POST /api/instruction/parse
```

请求：

```json
{
  "ocr_text": "Vision识别出的说明书文字"
}
```

建议返回：

```json
{
  "name": "药名",
  "spec": "规格",
  "dose": "一次用量",
  "frequency": "每日次数或频次",
  "meal_time": "饭前/饭后/不明确",
  "method": "服用方式",
  "location": "说明书贮藏方式",
  "expiry": "有效期",
  "risks": ["风险提示"],
  "contraindications": ["禁忌"],
  "precautions": ["注意事项"],
  "speech_text": "语音播报文案",
  "original_text": "后端收到的OCR原文",
  "used_sample_fallback": false,
  "fallback_fields": [],
  "needs_confirmation": true
}
```

后端这块需要重点处理：

1. 不要再用布洛芬或其他演示药品作为兜底结果。
2. 如果解析不出来，就返回空字段、`needs_confirmation = true` 和 `fallback_fields`，不要编造完整用药信息。
3. 保留并返回 `original_text`，方便前端展示和排查。
4. 支持从说明书常见字段中抽取信息，例如：
   - `【药品名称】`
   - `通用名称`
   - `商品名称`
   - `规格`
   - `用法用量`
   - `禁忌`
   - `注意事项`
   - `贮藏`
   - `有效期`
5. 对 OCR 噪声做基础清洗，例如多余空格、换行断句、中文标点混乱、序号拆行、栏目标题识别不完整。
6. `contraindications`、`precautions`、`risks` 建议统一返回数组；如果后端暂时返回字符串，前端也能兼容，但长期建议统一数组。
7. 药名查询输入可能只有一个药名，例如“阿莫西林”。这种情况下后端可以只返回能确定的字段，其他字段留空并标记需要核对，不要返回固定示例数据。

判断责任边界：

- 前端负责：拍照 / 选图、Vision OCR、把 OCR 原文发送给后端、展示 OCR 原文和结构化字段。
- 后端负责：把 OCR 原文解析成药名、规格、用法用量、禁忌、注意事项等结构化字段。
- 当前“识别结果很差”主要表现为结构化字段不准，因此优先由后端修 `/api/instruction/parse`。

### P1：补齐家庭成员接口

需要支持：

```text
GET /api/members
POST /api/members
DELETE /api/members/{member_id}
```

当前前端已经接入 `GET /api/members` 和 `POST /api/members`。左划删除成员时会调用 `DELETE /api/members/{member_id}`；如果后端暂时没有该接口，删除只会在前端当前会话里生效，刷新后成员可能重新出现。

注意：前端已把 `GET /api/members` 成功返回的空数组视为真实状态，方便后端删除到最后一个成员时同步为空列表。

建议成员数据包含：

```json
{
  "id": 1,
  "emoji": "🙂",
  "name": "爸爸",
  "role": "家庭成员",
  "status": "",
  "age": "",
  "weight": "",
  "allergy": ""
}
```

### P1：补齐药品接口

需要支持：

```text
GET /api/medicines
POST /api/medicines
PUT /api/medicines/{medicine_id}
DELETE /api/medicines/{medicine_id}
```

前端现在把“编辑药箱信息”和“信息已核对，标记正常”都接到了 `PUT /api/medicines/{medicine_id}`。后端需要保证：

1. `PUT` 是更新已有药品，不能创建新药品。
2. 药品业务接口能持久化并返回更新后的 `owner`、`location`、`stock`、`expiry_date`、`dose`、`frequency`、`meal_time`、`method`、`category`、`status`、`note` 等字段。页面内部仍使用 `Medicine.expiry` 展示，`BackendClient` 负责与 `expiry_date` 转换；说明书解析接口的 `expiry` 保持不变。
3. 当用户点击“信息已核对，标记正常”时，前端会把 `status` 更新为 `正常`；后端应保存这个状态，刷新后首页不应继续把该药显示为待核对。
4. 如果后端将来支持更细的药品状态，建议保留兼容值：`正常`、`需确认`、`识别不完整`、`即将过期`、`库存不足`。

建议药品数据里区分：

- `storage_method`：说明书贮藏方式，例如“阴凉处保存”
- `home_location`：家中实际位置，例如“卧室床头柜”

如果后端暂时只有 `location` 字段，也可以先用，但长期容易混淆。

药品归属建议支持两类：

```text
owner = "我" / "爷爷" / "奶奶" / ...
owner = "全部人"
```

`owner = "全部人"` 表示家庭共享药，不代表所有人都有服药任务。

### P1：持久化生产日期和保质期

药品表、创建接口、更新接口和响应模型需要增加：

```text
production_date TEXT NOT NULL DEFAULT ''
shelf_life TEXT NOT NULL DEFAULT ''
```

药品接口应持久化并原样返回：

```json
{
  "production_date": "",
  "shelf_life": "36个月",
  "expiry_date": ""
}
```

最终结构化契约中，`expiry_date` 应当是具体日期或空字符串，`36个月` 应保存在 `shelf_life`。当前前端仅为兼容旧后端而允许通过 `expiry_date` 往返保质期文本；后端升级和迁移完成后可以移除该兼容逻辑。当 `production_date` 为空时，前端使用 `shelf_life` 展示；当生产日期存在时，前端计算并提交具体 `expiry_date`。后端应校验日期格式，并建议复算或校验 `production_date + shelf_life` 与 `expiry_date` 是否一致；同时允许用户按包装直接提供明确到期日。

### P1：补齐提醒接口

需要支持：

```text
GET /api/reminders
POST /api/reminders
DELETE /api/reminders/{reminder_id}
```

提醒最好绑定 `medicine_id`，不要只存药名。

原因是同名药可能属于不同成员、不同规格、不同位置。

提醒必须绑定具体成员：

```json
{
  "medicine_id": 12,
  "medicine_name": "药名",
  "member_name": "爷爷",
  "time": "08:00",
  "meal_label": "饭后",
  "dose": "1片",
  "status": "待服药"
}
```

不要允许 `member_name = "全部人"` 的提醒进入确认服药流程。

### P1：删除药品时处理关联提醒

当前后端 `DELETE /api/medicines/{medicine_id}` 只删除药品，提醒表又只保存 `medicine_name`。前端会取消本机中能够匹配到的待触发系统通知并暂时隐藏提醒，但刷新后提醒仍会从后端重新出现；按药名调用后端级联还可能误删同名、不同规格或不同成员的提醒。

建议后端这样调整：

1. `reminders` 增加非空 `medicine_id` 外键，创建提醒时必须提交真实药品 ID。
2. 删除药品应在同一事务中删除或停用该药品尚未执行的提醒。
3. 已产生的服药记录属于历史数据，不应随药品删除；记录中保留药名快照，并允许关联药品/提醒为空，或采用软删除方案。
4. 返回删除结果前完成关联处理，前端刷新后不应再次看到已删除药品的活动提醒。
5. 数据迁移时不能只凭药名自动关联同名药，应结合成员、规格等信息，无法可靠匹配的记录留待人工确认。

在后端提供可靠的 `medicine_id` 关联前，前端不会按药名调用批量删除提醒，以免误删。

### P1：补齐服药记录接口

需要支持：

```text
GET /api/records
POST /api/records
DELETE /api/records/{record_id}
```

用户点“已服药”后创建记录。

用户点错后删除或撤销记录。

后端创建服药记录时需要校验：

- `reminder_id` 是否存在
- `member_name` 是否和提醒所属成员一致
- 老人模式下当前老人是否只能操作自己的提醒

即使前端已经限制，后端也应该拒绝“爷爷确认我的提醒”这种请求。

### P1：今日状态接口

需要支持：

```text
GET /api/today
```

返回今日每条提醒的状态，建议包含：

```json
{
  "reminder_id": "提醒ID",
```

### P2：库存扣减和回滚

用户确认已服药后，库存应该减少。

用户取消已服药后，库存应该加回来。

推荐由后端处理库存变化，因为库存需要持久保存。如果后端暂时不做，前端可以先本地显示，但刷新后可能丢失。

建议规则：

1. `POST /api/records` 成功后，按提醒绑定的 `medicine_id` 扣减库存。
2. `DELETE /api/records/{record_id}` 成功后，回滚对应库存。
3. 如果药品是合并展示的共享药，后端仍然应该按真实药品记录扣减，前端只负责展示合并库存。

## 4. OCR 测试说明

现在可以继续放图片测试 OCR。建议优先测这三类：

1. 药盒正面：药名、规格比较清楚。
2. 说明书局部：包含“用法用量 / 禁忌 / 注意事项”。
3. 模糊或角度偏的图片：确认前端会提示重新拍摄，而不是生成假卡片。

测试时请注意：

- 模拟器可以用“相册选择”。
- 真机可以用“打开相机”，需要允许相机权限。
- OCR 是前端本地 Vision 识别；后端负责解析文字。
- 后端 `/api/instruction/parse` 如果不可用，前端会生成“待核对药品”卡片并保留原始 OCR 文本，不再套用布洛芬等示例药。
- 如果 OCR 原文基本正确但卡片字段很差，请优先让后端修解析接口。

## 5. 当前前端后续还建议改的点

这些不是本次必须修改，但建议后续排期：

1. 生产日期与保质期字段需要后端完成持久化，否则只有最终 `expiry_date` 能稳定保存。
2. 提醒、服药记录、库存扣减和回滚需要后端持久化支持，否则刷新后可能回到后端旧状态。
3. 提醒最好从只绑定药名升级为绑定 `medicine_id`，避免同名药、不同成员或不同规格混在一起。
4. 如果合并药品组需要支持“一次编辑整组”，后端需要提供批量更新或明确合并组 ID；当前前端只编辑详情页代表的单条药品记录。
5. 家庭成员删除后，是否级联处理该成员药品、提醒、记录，需要产品和后端确认规则。
6. 后端需要对老人模式的成员归属做权限校验，不能只依赖前端过滤。
